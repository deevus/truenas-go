# Research: Go monorepo exemplars for `truenas-go` + Terraform provider facade

## Summary

The proposed canonical module (`github.com/deevus/truenas-go`) with public library packages plus `cmd/` and provider implementation in `internal/` is idiomatic Go: several mature projects keep importable packages, commands, and private implementation in one repository/module. The Terraform Registry-facing release-only facade is the non-standard/custom part: Terraform’s official publishing model expects a public GitHub repository named `terraform-provider-{NAME}` with semver GitHub releases and version-bound docs, while Kubernetes-style automated downstream publishing shows that mirrors can be legitimate but require explicit automation and ownership.

## Findings

1. **A single canonical Go module with public packages and commands is idiomatic.** `containerd` and `x/tools` both keep importable packages and `cmd/` binaries in the same repo/module, while clearly treating command and `internal` packages as outside the public API surface. [containerd RELEASES.md](https://github.com/containerd/containerd/blob/main/RELEASES.md), [x/tools README/tree](https://github.com/golang/tools)
2. **`internal/provider` is the idiomatic Terraform provider implementation boundary, but `cmd/` is not required by HashiCorp’s scaffold.** The official framework scaffold uses root `main.go` importing `internal/provider`; moving the provider entrypoint to `cmd/terraform-provider-truenas` is Go-idiomatic but differs from the scaffold. [scaffold README](https://github.com/hashicorp/terraform-provider-scaffolding-framework/blob/main/README.md), [scaffold main.go](https://github.com/hashicorp/terraform-provider-scaffolding-framework/blob/main/main.go)
3. **Multiple modules become idiomatic when version/release boundaries differ.** `grpc-go` splits `cmd/protoc-gen-go-grpc` into its own module, and OpenTelemetry-Go uses module sets with independent stable/experimental versions. [grpc nested go.mod](https://github.com/grpc/grpc-go/blob/master/cmd/protoc-gen-go-grpc/go.mod), [OpenTelemetry VERSIONING.md](https://github.com/open-telemetry/opentelemetry-go/blob/main/VERSIONING.md)
4. **Terraform Registry compatibility creates a naming/release constraint that a normal Go monorepo does not satisfy by itself.** Official Terraform docs require public GitHub repos named `terraform-provider-{NAME}`, semver `vMAJOR.MINOR.PATCH` GitHub Releases, signed checksums, and docs in `docs/` tied to each provider version. [Publishing providers](https://developer.hashicorp.com/terraform/registry/providers/publishing), [Provider docs](https://developer.hashicorp.com/terraform/registry/providers/docs)
5. **A downstream facade/mirror is a proven pattern, but not a default Go or Terraform-provider convention.** Kubernetes proves the mechanics and governance model: authoritative code in one repo, bot-published downstream repos, read-only contribution policy. A Terraform release-only facade would be custom automation applying a similar idea to Registry ingestion rather than a commonly documented Terraform layout. [Kubernetes staging README](https://github.com/kubernetes/kubernetes/blob/master/staging/README.md), [client-go README](https://github.com/kubernetes/client-go)

## Verdict for `truenas-go`

The proposed layout is idiomatic if the main compatibility promise is the Go client library: keep `github.com/deevus/truenas-go` as canonical, expose root/client/api packages, place the Terraform provider command under `cmd/`, and keep provider implementation under `internal/`. If the provider needs independent versioning from the library, consider a nested provider module or separate provider repo; otherwise, one module is acceptable but couples provider and library tags. The release-only GitHub facade for Terraform Registry compatibility is custom rather than idiomatic: it should be documented as generated/read-only, with automated release mirroring, signed artifacts, and version-bound docs.

## Gaps

- I did not find a primary-source Terraform provider that exactly combines: public Go client library, provider under `cmd/`, private provider implementation under `internal/`, provider docs/release metadata in the same canonical repo, and a release-only Registry facade. The recommended next step is to document the facade contract explicitly and automate it, rather than treating it as standard Terraform-provider practice.
